# Lixel OpenAPI Developer Guide

This manual targets developers building on the Lixel device OpenAPI (based on
MQTT + Protobuf). It covers the protocol architecture, connection and
authentication, message codec, the full interface catalog, and the reusable
client wrapper, GUI control panel, and example scripts shipped with this project.

- Protocol: MQTT / MQTTS
- Payload: Protobuf binary (except the heartbeat, which is JSON text)
- Proto package: `openapi.aiot_msgs`
- Proto source: `proto/openapi/aiot_msgs.proto`

> A Chinese version of this manual is available at `docs/lixel_openapi_developer_guide_zh.md`.

## 1. Architecture

The device and client communicate through an MQTT broker (running on the
device). All business messages are serialized with Protobuf and carried as the
MQTT payload. Topics use a three-segment naming scheme:

```
lixel/<domain>/<type>/<name>
```

- `domain`: business domain, mainly `application` in this protocol
- `type`: message direction
  - `request`  client → device (request)
  - `response` device → client (reply to a request)
  - `report`   device → client (active push)
- `name`: specific feature, e.g. `device_info`, `modeling`

There are two typical interaction patterns:

- **Request-response**: the client publishes to `.../request/xxx` and subscribes
  to `.../response/xxx` to await the reply.
- **Subscribe-report**: the client subscribes to `.../report/xxx` and passively
  receives data pushed by the device.

```
┌────────────┐   publish request    ┌──────────────┐
│            │ ───────────────────► │              │
│  Client    │                      │   Device     │
│ (this app) │ ◄─────────────────── │ (MQTT Broker)│
│            │   response / report  │              │
└────────────┘                      └──────────────┘
```

## 2. Connection & Authentication

### 2.1 Connection Parameters

Each product model supports only one of the connection modes (not both):

| Protocol | Port | Username | Password | Product model |
|----------|------|----------|----------|---------------|
| MQTT | 1883 | - | - | K1/L2PRO |
| MQTTS | 8883 | *(provided by the vendor)* | *(provided by the vendor)* | Other products (except K1/L2PRO) |

> K1/L2PRO support MQTT only; other products support MQTTS only. Each product
> supports exactly one protocol.

> MQTTS uses TLS. The examples in this project disable certificate verification
> by default (`CERT_NONE` + `tls_insecure`) to work with the device's
> self-signed certificate. When MQTTS is selected in the GUI, enter the
> username/password provided by the vendor manually.

### 2.2 OpenAPI Key Authentication

Most request messages carry an optional `openapi_key` field in the `Header`,
which the device uses to validate the request. **The OpenAPI Key is provided by
XGRIDS** — just fill it in when developing; you do not need to generate it
yourself.

- GUI: enter it in the "OpenAPI Key" field of the top connection bar. When you
  "Load template" for publishing, it is written into `header.openapi_key`
  automatically.
- Code: set `ClientOptions.openapi_key`, and `request()` / `publish()` fill it
  into `header.openapi_key` automatically.

```python
from example.core import ClientOptions, OpenApiClient

opts = ClientOptions(host="192.168.55.1", openapi_key="<provided by XGRIDS>")
with OpenApiClient(opts) as client:
    ...  # header.openapi_key is filled automatically
```

### 2.3 Common Header Fields

The first field of every request/response/report message is usually a `Header`:

| Field | Type | Description |
|-------|------|-------------|
| `seq` | uint32 | Frame sequence number |
| `stamp` | sint64 | Frame timestamp |
| `scaler` | sint64 | Scale factor (used by point cloud, etc.) |
| `device_id` | string | Device ID (generated by the device) |
| `session_id` | string | Session ID (generated by the request/report side) |
| `openapi_key` | string | API key (optional) |

## 3. Message Model & Codec

### 3.1 Proto Compilation

Use the bundled script to compile `proto/openapi/aiot_msgs.proto` into the
Python module `src/proto_gen/openapi/aiot_msgs_pb2.py`:

```bash
python src/generate_proto.py
```

> Generation uses the current environment's `grpc_tools.protoc`, keeping the
> gencode version consistent with the runtime protobuf version. At runtime it is
> recommended to set `PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION=python` (already the
> default in this project) to avoid upb C-extension incompatibilities across
> environments.

### 3.2 JSON ↔ Protobuf

The project's core provides `ProtoCodec`, based on
`google.protobuf.json_format`, to convert between dict/JSON and protobuf binary:

```python
from example.core import ProtoCodec

codec = ProtoCodec()

# Encode: dict → protobuf binary
data = codec.encode("DeviceControlRequest", {"action": "AC_SYSTEM_REBOOT"})

# Decode: protobuf binary → dict
result = codec.decode("DeviceControlResponse", data)

# Generate a default template (with all fields)
template = codec.default_json("ModelingRequest")
```

Notes:

- Enum fields accept the enum name string (e.g. `"AC_START"`) or the integer value.
- `bytes` fields appear as base64 strings in the dict.
- Field names keep the proto snake_case (`preserving_proto_field_name=True`).

## 4. Interface Catalog

The following interfaces correspond exactly to `aiot_msgs.proto`. Direction
markers: `REQ`=request, `RSP`=response, `RPT`=report. All topics are prefixed
with `lixel/application/`.

### 4.1 Status Monitoring

| Interface | Direction | Topic (prefix omitted) | Message | Description |
|-----------|-----------|------------------------|---------|-------------|
| Device heartbeat | RPT | report/heartbeat | *(JSON)* | Heartbeat broadcast, for discovery |
| Device status | RPT | report/device_status | DeviceStatusReport | Mapping/system/RTK status at 1 Hz |
| Realtime pose | RPT | report/lio_pose | LioPoseReport | Realtime LIO pose while scanning |
| Realtime point cloud | RPT | report/lio_pcl | MqttCompressMsg | Compressed realtime point cloud |
| System error | RPT | report/system_error | SystemErrorReport | System error code report |

The heartbeat payload is JSON text, e.g.:

```json
{"DeviceSN":"A256A60000","Timestamp":1697703246.5,"ProtocolVersion":"3.0.0"}
```

The realtime point cloud `MqttCompressMsg` needs a second decompress/decode:

1. Deserialize `MqttCompressMsg` to get `compression` (Lz4/Zstd) and `compressed_data`
2. Decompress `compressed_data` according to the compression type. Lz4 data is a raw
   LZ4 block (not the LZ4 frame format) and needs the original size, which is
   `compressed_size` (the size before compression)
3. Deserialize the result as `LioPclReport` to obtain the point array

### 4.2 Device Management

| Interface | Direction | Topic (prefix omitted) | Message |
|-----------|-----------|------------------------|---------|
| Query device info | REQ / RSP | request/device_info · response/device_info | DeviceInfoRequest / DeviceInfoResponse |
| Device config | REQ / RSP / RPT | request·response·report/device_config | DeviceConfigRequest / DeviceConfigResponse |
| Device control | REQ / RSP | request/device_control · response/device_control | DeviceControlRequest / DeviceControlResponse |

Device control supported `ActionCmd`: `AC_USB_MASS`, `AC_USB_ETHER`,
`AC_DISK_FORMAT`, `AC_POWER_OFF`, `AC_SYSTEM_REBOOT`.

### 4.3 Scan Mapping

| Interface | Direction | Topic (prefix omitted) | Message |
|-----------|-----------|------------------------|---------|
| Scan control | REQ / RSP / RPT | request·response·report/modeling | ModelingRequest / ModelingResponse / ModelingReport |
| Current project file URLs | REQ / RSP | request/modeling_status · response/modeling_status | ModelingStatusRequest / ModelingStatusResponse |

Scan `action` supports `AC_START` / `AC_STOP`. Key `ModelingRequest` fields:
`project_name`, `record_mode` (RM_CALC/RM_RECORD/RM_RECORD_CALC),
`scan_mode` (SM_PCL/SM_LCC/SM_PORTRAIT),
`mount_type` (MT_HAND/MT_CAR/MT_UAV/MT_BACKPACK),
`assist_mode` (AM_GUIDED/AM_VISUAL).

### 4.4 Point Management

| Interface | Direction | Topic (prefix omitted) | Message |
|-----------|-----------|------------------------|---------|
| Control point operations | REQ / RSP / RPT | request·response·report/control_point | ControlPointRequest / ControlPointResponse / ControlPointReport |
| Measure point operations | REQ / RSP | request/measure_point · response/measure_point | MeasurePointRequest / MeasurePointResponse |

Control point `action` supports `AC_ADD` / `AC_REMOVE`. `AC_UPDATE` is defined in the proto, but the device does not handle it
and returns `EC_ProtoError` (`desc` is `invalid action`).
In standby the device does not reply to control point requests. `AC_ADD` ignores the `id` in the
request; the `id` in the response is chosen by the device and must be used to remove the point. On success the `error.desc` of
`AC_ADD` is the pose of the point (7 floating point numbers separated by spaces), not a text description.
measure point `action` supports `AC_ADD` / `AC_REMOVE` only.

> ⚠️ **The measure point feature is supported on some devices only.** Please
> verify that your target device provides this capability.

### 4.5 Project Management

| Interface | Direction | Topic (prefix omitted) | Message |
|-----------|-----------|------------------------|---------|
| Project list operations | REQ / RSP | request/project_list · response/project_list | ProjectListRequest / ProjectListResponse |

`action` supports `AC_LIST_ALL_PROJECTS` (list), `AC_MODIFY_PROJECT_LABELS`
(modify label, needs `id` + `tag_name`), `AC_DELETE_PROJECTS` (delete, needs
`id_list`).

### 4.6 RTK / Ntrip

| Interface | Direction | Topic (prefix omitted) | Message |
|-----------|-----------|------------------------|---------|
| Get Ntrip profile | REQ / RSP | request/get_ntrip_profile · response/get_ntrip_profile | GetNtripProfileRequest / GetNtripProfileResponse |
| Set Ntrip profile | REQ / RSP | request/set_ntrip_profile · response/set_ntrip_profile | SetNtripProfileRequest / SetNtripProfileResponse |
| Get RTK advanced config | REQ / RSP | request/get_rtk_advance · response/get_rtk_advance | GetRtkAdvanceRequest / GetRtkAdvanceResponse |
| Set RTK advanced config | REQ / RSP | request/set_rtk_advance · response/set_rtk_advance | SetRtkAdvanceRequest / SetRtkAdvanceResponse |

Set Ntrip `action` supports `AC_LOGIN` / `AC_LOGOUT`; CORS type
`CUSTOM/QIANXUN/ZHONGYI`; coordinate frame `UNKNOWN/ITRF2008/WGS84/CGCS2000`.
RTK satellite systems support `GPS/BDS/GLO/GAL/QZSS/IRNSS`.

> ⚠️ **Special note on `SetNtripProfileRequest`**: setting is only allowed when
> the RTK status is `HwConnected`. When the device WiFi is in AP mode (Ntrip data
> is then forwarded over WebSocket), sending this request makes the Response
> return error code `AppCode::EMBError::Unknown`; this error can be ignored and
> the device's Ntrip connection is not affected at all.

### 4.7 Data Processing

| Interface | Direction | Topic (prefix omitted) | Message |
|-----------|-----------|------------------------|---------|
| Data unpack | REQ / RSP / RPT | request·response·report/data_unpack | DataUnpackRequest / DataUnpackResponse / DataUnpackReport |

`data_source` currently supports `XBIN_DATA`; if `data_topics` is omitted,
everything is unpacked; `report/data_unpack` reports the unpack progress (0~100).

> ⚠️ **The data processing (unpack) feature is supported on some devices only.**
> Please verify that your target device provides this capability.

### 4.8 Error Code Convention

Request-response messages carry error info in the `Error error = 15` field
(`code` + `desc`). Common error codes: `EC_RequestSuccess`, `EC_RequestError`,
`EC_ProtoError`; Ntrip-related: `EC_NtripLoginSuccess`, `EC_NtripLogoutSuccess`,
`EC_NtripLogoutFailed`, `EC_NtripDisConnected`, `EC_NtripNetworkError`,
`EC_NtripAuthError`.

## 5. core Client Wrapper

`example/core` provides a reusable, Qt-free wrapper and is the recommended entry
point for secondary development.

### 5.1 Modules

| Module | Description |
|--------|-------------|
| `api_catalog.py` | Single source of truth for the interface catalog (`ApiInterface` / `Endpoint` / `Direction`) |
| `proto_codec.py` | `ProtoCodec`: JSON ↔ protobuf codec, default template |
| `openapi_client.py` | `OpenApiClient` / `ClientOptions`: MQTT connection, request-response, subscription |

### 5.2 ClientOptions

```python
from example.core import ClientOptions

opts = ClientOptions(
    host="192.168.55.1",
    port=1883,
    use_tls=False,          # set True for MQTTS
    username="",
    password="",
    openapi_key="",         # written into header.openapi_key automatically
    device_id="",
    connect_timeout=10.0,
    request_timeout=10.0,
)
```

### 5.3 Request-Response

```python
from example.core import OpenApiClient, ClientOptions

with OpenApiClient(ClientOptions(host="192.168.55.1")) as client:
    rsp = client.request(
        req_topic="lixel/application/request/device_info",
        req_message="DeviceInfoRequest",
        payload={},                       # dict or JSON string
        rsp_topic="lixel/application/response/device_info",
        rsp_message="DeviceInfoResponse",
    )
    print(rsp)                            # decoded dict
```

Inside `request()`: subscribe to the response topic → publish the request →
block until the first response → decode and return; raises `TimeoutError` on
timeout.

### 5.4 Subscribe to Reports

```python
def on_status(topic, data):   # data is already decoded into a dict
    print(topic, data)

client.subscribe(
    "lixel/application/report/device_status",
    "DeviceStatusReport",
    on_status,
)
```

For JSON payloads (heartbeat), pass an empty string for `message`, and the
callback receives a string.

### 5.5 API Overview

| Method | Description |
|--------|-------------|
| `connect()` / `disconnect()` | Connect / disconnect (supports `with` context) |
| `is_connected` | Connection status |
| `publish(topic, message, payload)` | Publish a message |
| `subscribe(topic, message, callback)` | Subscribe and register a callback |
| `unsubscribe(topic)` | Unsubscribe |
| `request(...)` | Synchronous request-response call |
| `codec` | Built-in `ProtoCodec` |

## 6. GUI Control Panel

`example/main.py` provides a graphical control panel with a "Publish" panel on
the left and a "Subscribe" panel on the right (same layout as the OpenAPI MQTT
Debugger).

```bash
python example/main.py                 # English UI by default
python example/main.py --lang zh       # Start in Chinese (also switchable in the menu)
```

UI structure:

- Menu bar:
  - Settings → Language: switch between English/Chinese live (**English by
    default**), no restart required
  - About: shows the program version injected at build time (`V0.0.0` when run from source)
- Top connection bar: Host / Port / Protocol (MQTT·MQTTS) / Username / Password /
  OpenAPI Key / Connect
  - Default host is `192.168.55.1`
  - Username/Password are shown only when MQTTS is selected; enter the
    credentials provided by the vendor (hidden and cleared when switching back
    to MQTT)
- Left "Publish" panel (same as the OpenAPI-XPanel):
  - Topic dropdown (editable, prefilled with all publishable request topics)
  - Message type dropdown (Request types only) + Load template (Request types only)
  - Description area: shows the feature description and notes of the selected
    topic, and reminds you which response topic to subscribe to on the right
  - JSON editor + Publish button
  - Selecting a Topic auto-syncs the message type; "Load template" generates a
    default JSON and injects the header
    (seq/stamp/device_id/session_id + openapi_key)
- Right "Subscribe" panel (same as the OpenAPI-XPanel):
  - Topic dropdown (editable) + Subscribe / Subscribe all
  - Wildcard subscription (default `lixel/#`)
  - Current subscription list + Unsub selected / Unsub all
  - Received messages (summary list, auto scroll) + View detail / Clear;
    double-click to see the full decoded content

> Publishing only sends a request and does not block the UI; **responses and
> reports are all viewed in the "Subscribe" panel on the right.** So before
> publishing a request, subscribe to the corresponding response topic first (or
> use the wildcard `lixel/#`). The panel auto-decodes by matching the message
> type to the topic; unknown types or JSON payloads (heartbeat) are shown as
> text, binary as a HEX summary, and long fields are truncated automatically.

## 7. Example Scripts

`example/usage/` provides a standalone, runnable script for each interface — the
most direct reference for secondary development. All are based on
`OpenApiClient` and do not depend on the GUI.

```bash
cd example/usage
python device_info.py --host 192.168.55.1 --port 1883 --key <your OpenAPI Key>
python modeling.py --project demo --watch 5 --key <your OpenAPI Key>
python heartbeat.py --seconds 15
```

Common arguments: `--host/--port/--tls/--username/--password/--key/--timeout`. Requests
without a valid OpenAPI Key are rejected with `EC_ProtoError` (`openapi auth error`), so always pass `--key`.
`modeling.py` waits until the device is really scanning before it starts counting `--watch`,
and waits for standby after stopping, so a run takes a minute or more (71 s was measured with `--watch 10` on a Lixel L2Pro).
See `example/usage/README.md` for the full list of scripts.

> `lio_pcl.py` demonstrates point cloud decompression and requires
> `pip install lz4 zstandard`; without them the script prints a hint and skips
> point cloud decoding.

## 8. Localization (i18n)

All user-visible English source text in the GUI is wrapped with Qt's `self.tr()`;
translations are stored in `example/i18n/openapi_zh.ts` (source language en_US,
target zh_CN).

```bash
# Extract translatable strings from source (update .ts)
bash example/i18n/build_i18n.sh update

# Compile .ts into .qm
bash example/i18n/build_i18n.sh release
```

Underneath it calls the system Qt tools `lupdate` / `lrelease`. The UI is
**English by default** and can be switched live from the "Settings → Language"
menu (no restart required); you can also specify it at startup with
`--lang <code>`:

```
example/i18n/openapi_<lang>.qm
```

To add a language: copy the `.ts` and translate → compile with `lrelease` →
register it in `LANGUAGES` in `control_panel.py` → it appears in the menu.

## 9. FAQ

**Q: Connection timeout?**
Check the device host/port and whether the protocol matches (1883=MQTT,
8883=MQTTS); MQTTS needs a username/password. The core client's `connect()`
raises `TimeoutError` on timeout.

**Q: No response / request timeout?**
Confirm the request topic matches the message type and the device is in a state that
can respond. Note that some requests are not answered while the device is in standby
(for example `modeling_status` and `control_point`). A missing or wrong `openapi_key`
is answered immediately with `EC_ProtoError` and `desc` set to `openapi auth error`, so it is not a timeout. `request()` defaults to a
10 s timeout, adjustable via `--timeout` or `request_timeout`.

**Q: Protobuf version error?**
Run `python src/generate_proto.py` to regenerate, keeping the gencode consistent
with the runtime version; this project uses the pure-Python implementation by
default to avoid C-extension incompatibilities.

**Q: Point cloud decode fails?**
Install the decompression deps `pip install lz4 zstandard`, and make sure the
device is scanning so that point clouds are reported.
Lz4 data is a raw LZ4 block; decompress it with
`lz4.block.decompress(data, uncompressed_size=compressed_size)`. Using `lz4.frame`
fails with `ERROR_frameType_unknown`.

**Q: How to fill enum fields?**
Use the enum name string (recommended, e.g. `"AC_START"`) or the integer value.
